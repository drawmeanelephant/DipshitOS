## Notes

Deterministic claim ID from `bash tools/status/claim-id.sh '<branch>' 'alloc-loader-boot-pooling'` = 5162.

**Why this card:** claim 3972 explicitly deferred loader/boot-services pooling because it needs kernel-image + map-buffer exclusion ranges. This claim lands those ranges. The kernel image (loader_code), stack (loader_data), handoff struct page (loader_data), and captured-map buffer (loader_data) are the only loader/boot allocations still live after ExitBootServices; everything else in those regions is dead firmware/loader residue and safe to reclaim. Runtime code/data is deliberately NOT pooled (ResetSystem/SetVariable still run through the runtime services table post-exit).

**Design (all additive to the claim-3972 bitmap allocator):**

1. **Pooled types:** `is_poolable` = conventional, loader_code, loader_data, boot_services_code, boot_services_data. Runtime/persistent/ACPI/reserved/MMIO stay unpooled (bits set).
2. **Exclusions:** `pub const Exclusion = struct { base: u64, pages: u64 }` + `exclusion_from_bytes(base, bytes)` (rounds base down / size up to whole pages). `State.init(view, exclusions)` runs a third pass after pooling: each exclusion's overlap with pooled regions has its bits set back to allocated; only 0→1 transitions count toward `Stats.excluded_pages`, so exclusions over gaps are no-ops and `free_count = total − excluded` stays exact. `alloc_pages` can never return an excluded page (its bit is set).
3. **Kernel wiring (`kernel_main`):** exclusions = handoff kernel image, handoff stack, the handoff page itself, and the captured-map buffer. The span now extends to the highest pooled region end (still capped at the 4 GiB identity-map blanket); the fixed 128 KiB BSS bitmap covers it.
4. **Observability:** `pages` prints `excluded=…`; `pages selftest` restore check now compares against the initial free count (free < total is by design when exclusions exist).
