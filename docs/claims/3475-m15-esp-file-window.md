## Notes

**Why this card:** M1.5's definition of done lists `ls`/`cat`/`write` and hard gate 5 ("persist through reboot") is the only acceptance item left open. Post-exit there is no ESP root / Simple File System (x3 carries handoff v2, ADR 0004 D5), so the milestone's own step-15 plan names the pre-exit file window as the in-scope path. Design choices:

1. **Snapshot pre-exit, serve post-exit.** `esp.snapshot_esp(st, image_handle)` walks the ESP root (via the loader's image handle from handoff v2) before `ExitBootServices`, recording each entry's name/size and content for files ≤ 2 KiB (bounded BSS pool). `ls` lists everything; `cat` prints snapshotted content and honestly reports "not snapshotted (too large)" / "is a directory" otherwise.
2. **`write` persists via runtime variables.** Post-exit there is no writable filesystem, but runtime `SetVariable` is proven alive on VZ (claims 0009/0015, ≤ ~512 B values) and the runner's `VZEFIVariableStore` file survives across boots/runs. `write <name> <text...>` stores the content as non-volatile variable `DipshitF:<name>` (≤ 384 B, ≤ 8 files) and updates the in-memory window; `ls`/`cat` merge a runtime-variable scan (`GetNextVariableName`/`GetVariable`) back in, so files written in a previous boot are visible — persistence through reboot, honestly labeled `[nvram]`.
3. **Honesty rules.** A failed/absent runtime call never changes control flow; `write` reports the exact failure (no runtime services / SetVariable status / name or size limits). NVRAM files are explicitly the persistence medium (not a FAT write); the ESP itself stays read-only this milestone (full storage driver remains deferred). All limits fixed and explicit; no allocation beyond fixed BSS.
