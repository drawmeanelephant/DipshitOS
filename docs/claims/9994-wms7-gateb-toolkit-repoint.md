## Scope — the toolkit re-point (the issue's in-scope item 3 + its acceptance gate)

Gate A froze the wire + the WM server half. Gate B delivers the APP half of "ask the WM":

1. **`user/src/lib/ui.zig` — a WM_RPC client.** The toolkit gains a fully self-contained client:
   - A FROZEN wire mirror of `wnd_core.WmRpc` (kind / id / seq / reply_to / applied / pad / u16 rect / ≤24-byte title — byte-identical layout, host-tested against the frozen values). `lib/ui.zig` is compiled into 28 app modules whose Zig module paths cannot reach `kernel/src/`, so the cross-tree import is impossible; the frozen mirror + the live gate's byte-level round-trip (UI frame → WND.BIN parse → ack → `wnd: mail`) is the integration drift guard — a drift fails the gate loudly. The wmrpc host test additionally asserts `ui.wm_rpc_kind_*`/`ui.wm_rpc_max`/`ui.WmRpc` byte-size equal `wnd_core`'s (the strongest drift lock possible without a shared import).
   - `wm_peers(self_name)` — one `sys_procs` scan resolving (WM pid, self pid) for the ack's `reply_to`.
   - `wm_mail_request(kind, id, x, y, w, h, title, self_name, seq)` — builds the frame, `sys_ipc_send`s it to the WM's mailbox (slot 5), polls OUR OWN inbox (slot 6 — recv is per-caller) for the ack. Synchronous-shaped send+await — the issue's "async inversion" note answered (no async break; the WM serves at its 1 Hz kind-18 wake, ≤ 1 s).
   - `wm_raise_front(id, self_name)` / `wm_config(id, x,y,w,h, self_name)` — the re-pointed policy calls: try mail, fall back to the FROZEN syscalls (`sys_win_raise_front` slot 49 / `sys_win_move` slot 16) when no WM is registered — additive, byte-identical behavior.
2. **LIBUI.SO note (honest):** the shipped `LIBUI.SO` is generated by `tools/mkdyn-elf.py` as an ELF32 thunk library where each export is a BARE syscall proxy `(name, svc_num)` or hand-emitted asm. The message-shaped WM_RPC client is async (send + poll + fallback) and CANNOT be a bare syscall thunk — exposing it there would mean re-emitting the whole client in python-emitted AArch64 asm, duplicating `ui.zig` (two sources of the wire = drift). So the toolkit client lives in `lib/ui.zig` (what the issue calls "the toolkit"), is exercised end-to-end by WMRPC.BIN (a real toolkit app), and `libui_so.zig`/`ld.zig` are untouched. Dynamic-app (ELF) mail is out of scope; the `LdSymbol` test fixtures are synthetic and unaffected (real `.so` symbols parse from their symtab).
4. **WMRPC.BIN** (`user/src/wmrpc.zig`) — re-pointed to ride the toolkit: it already proves the raw round-trip (Gate A); now it calls `ui.win_raise_front` / `ui.win_config` so the live gate proves "a test app asked the WM through the toolkit" (the issue's acceptance). The `wnd: mail` server markers + `wmrpc: *-ack` app markers stay put (same wire), so the Gate-A gate re-runs unchanged.
5. **Back-compat:** with no WM, `ui.win_raise_front` / `ui.win_config` fall back to the frozen syscalls — apps that never send mail or run without a WM keep working. M11 desktop-app gates untouched (they don't call the re-pointed ops).

## Design decisions

1. **Relative import over per-module anon imports.** `wnd_core.zig` is std-only, so `lib/ui.zig` imports it by `@import("../../kernel/src/wnd_core.zig")`. This avoids touching all 28 `build.zig` app modules yet keeps the single-source wire format — the toolkit compiles the SAME `WmRpc` the server and kernel do, so the frames cannot drift.
2. **Synchronous-shaped API (explicitly, per the issue's async-inversion note).** `ui.win_raise_front` / `ui.win_config` are blocking calls that send + bounded-poll for the ack, so real app code does not become state machines. Latency is ≤ 1 s (the WM serves at its 1 Hz kind-18 wake) — accepted and documented, matching Gate A.
3. **Fallback is per-call, not cached-failure.** Each call discovers the WM via a cheap `sys_procs` scan; if absent it takes the frozen-syscall path immediately. No module-level WM-liveness cache (so no cross-call staleness and no writable-state change beyond what ui.zig already has).
4. **WMRPC.BIN stays the acceptance app.** It's the one EL0 test app the Gate-A gate already drives with `wnd start`+`exec NOTEPAD.BIN`+`exec WMRPC.BIN` (no args now: importing the toolkit grew WMRPC past the flat-DSK1 single-text-page argv cap, so the fixed gate topology — target 2 = NOTEPAD's window, WM = WND.BIN — is hardcoded and the exec takes no argv). Re-pointing it to the toolkit means the SAME gate now proves the toolkit, and a new no-WM boot (in this gate) proves the syscall fallback.
